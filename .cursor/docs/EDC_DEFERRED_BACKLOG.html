1. Flow หน้าร้าน — รอคุยกับลูกค้าและทีม

ปุ่ม "ชำระเงินแล้วค้าง?" ให้แคชเชียร์กดเอง

รอ consensus

ออกแบบไว้แล้วแต่ยังไม่ลงมือ — ตอนนี้ให้ dev ดูแลข้อมูลไปก่อน

รอเครื่อง 90 วิ │ ├─ เครื่องตอบ → flow ปกติ │ └─ ครบ 90 วิ → ขึ้นปุ่ม "ชำระเงินแล้วค้าง?" │ └─ กด → dialog ยืนยัน (ระบุว่าจะออกใบเสร็จ + ตัดสต็อก) │ └─ ยืนยัน → ใบเสร็จออก · สต็อกลด · สถานะ "รอตรวจสอบ" │ └─ background อีก 20 วิ ├─ เครื่องอนุมัติ → เปลี่ยนเป็น success └─ เครื่องปฏิเสธ → ??? ยังไม่ตัดสินใจ

เรื่องที่ต้องตัดสินใจก่อนทำ

เรื่องรายละเอียด
ช่องทุจริต ยิงของเข้าตะกร้า → เลือก EDC → ไม่ให้ลูกค้าจ่าย → รอ 90 วิ → กดปุ่ม → ใบเสร็จออก สต็อกลด แต่ไม่มีเงินเข้า
ตัวป้องกันคือสถานะ "รอตรวจสอบ" + การกระทบยอดกับ settlement ธนาคาร — เป็น detective control ไม่ใช่ preventive จึงต้องมีคนดูจริง
ต้องมีคนเห็น ถ้าโชว์แค่ในหน้าลับที่ไม่มีลิงก์ ไม่มี alert → control มีแต่ไม่ทำงาน
เสนอ: ให้รายการ "รอตรวจสอบ" โผล่ในรายงานที่บัญชี/ผู้จัดการดูทุกวันอยู่แล้ว (เช่นบรรทัด "EDC รอตรวจสอบ: 2 รายการ ฿1,340") — ไม่ต้องสร้างระบบแจ้งเตือนใหม่
ใบเสร็จจะบอกยังไงว่ารอตรวจสอบ pos_checkout_service.ts:295 บังคับว่า EDC ต้องมี edc_approval_code แต่เคสนี้ไม่มี
เสนอ: เพิ่มคอลัมน์ edc_verified ใน receipts (additive) ดีกว่าใส่ค่าปลอมแบบ PENDING-xxxx ที่จะไปปนกับ approval code จริงในรายงาน
ถ้า 20 วิแล้วเครื่องตอบ "ปฏิเสธ" ใบเสร็จออกไปแล้ว ของอาจส่งลูกค้าไปแล้ว
ตัวเลือก: auto-void (เสี่ยง สต็อกผิดอีกทาง) หรือ ขึ้นธงแดงให้คนตัดสิน (เชียร์อันนี้)
ตัวฟังผล 20 วิ อยู่ที่ไหน ตอนนี้ loop ที่ฟังผลอยู่ใน EdcPaymentModal — ถ้าแคชเชียร์กดปุ่มแล้ว modal ปิด component unmount → loop ตาย รอไม่ครบ 20 วิ
ต้องย้ายตัวฟังออกไปนอก modal
เช็คยอด amountsMatch() ทำไว้แล้วในระยะนี้ — ถ้าทำปุ่ม ต้อง block เมื่อยอดไม่ตรง ปิดช่อง "ใส่ของแพงแล้วรูดจริง 1 บาท"

timeout 90 วิ ที่ /txn/sale

รอ consensus

SDK ยิง POST /txn/sale โดยไม่มี timeout (paywire/client.ts:300) ถ้า bridge ไม่ตอบ loop ไม่จบ และตอน processing ปุ่ม Back ถูกซ่อน + dismissLocked → ค้างถาวร ต้อง F5

ข้อแลกเปลี่ยนที่ต้องรู้: timeout ยกเลิกรายการที่เครื่องไม่ได้ — ถ้าลูกค้าแตะบัตรวินาทีที่ 95 เงินจะตัดจริงทั้งที่จอขึ้น error ไปแล้ว กลายเป็นเคสค้างที่เราสร้างเอง
ตัวลดผลกระทบมีอยู่แล้ว: row started + cart_snapshot + pos_ref ที่ใช้ query() ได้

2. บั๊กที่รู้แล้วแต่พักไว้

Modal ค้างที่ "Recording receipt…" ถาวร

บั๊ก แก้ได้เลย ไม่ต้องรอใคร

เมื่อ checkout ล้มเหลว doCheckout ไม่ได้ปิด modal (setEdcOpen(false) อยู่แค่ใน success path) → step ค้างที่ approved → ปุ่มถูกซ่อน (step !== "approved") + dismissLocked → ปิดไม่ได้ ต้อง F5

timeout 30 วิ ที่ใส่ไปแล้วทำให้ รู้ ว่าพัง (มี toast) แต่ modal ยังค้างเหมือนเดิม — การแก้คือแค่ให้ปิด modal ได้เมื่อ checkout ไม่สำเร็จ ไม่ต้องตัดสินใจเรื่อง flow อะไรเลย

bridge error ยังโชว์ปุ่ม "Try again"

ตั้งใจไม่แตะ

ถ้า bridge ดับตั้งแต่แรก = ยังไม่ได้ส่งอะไรไปเครื่อง → retry ปลอดภัย จึงปล่อยไว้ แต่ถ้า bridge ดับ ระหว่าง รายการ retry จะเสี่ยงตัดซ้ำ — แยกสองกรณีนี้จากกันไม่ได้ง่ายๆ

3. ปิดไปแล้ว ไม่ต้องทำ

เคยวางแผนไว้ทำไมไม่ต้องทำ
เพิ่ม fallback fields["38"] สำหรับ approval code สมมติฐานตกไป — ข้อมูลจริงจาก prod (6 ส.ค. 17:24) แสดงว่า bridge ส่ง key ชื่อ approval_code ตรงๆ เป็น LinkPOS naming ล้วน ไม่มี VTI numeric field เลย ซึ่ง client.ts:339 อ่านอยู่แล้ว
ส่ง posRef เข้า sale() เพื่อให้ query() ใช้ได้ ไม่ต้องส่ง — bridge derive เองจาก idempotencyKey (20 ตัวแรก ตัดขีด) ยืนยันด้วยข้อมูลจริงแล้ว ดู posRefFromIdempotencyKey()
สร้าง intent ใน payment_intents (intent_type='pos_edc') ไม่ทำ — edc_txn_events ทำเรื่องสถานะไปแล้ว การเพิ่ม intent จะได้ตารางสองใบ ที่เล่าเรื่องเดียวกัน และ payment_intents.status เป็น PG enum 3 ค่า ที่ ALTER TYPE ใน migration transaction จะพัง
email แจ้ง dev เมื่อเจอรายการค้าง ตัดออกตามที่ตกลง (และ email ถูกปิดอยู่แล้วถ้า APP_ENV != prod)
แถบแจ้งเตือนในหน้า POS ตัดออก
แสดง POS REF ใน error dialog ไม่จำเป็นแล้ว ถ้าทำปุ่มแจ้งปัญหา (ระบบบันทึกเองไม่ต้องให้คนอ่านเลขทางโทรศัพท์)

4. ยังไม่มีคำตอบ — ต้นเหตุจริงของเคส 6 ส.ค.

ยังไม่ปิดเคส — วันที่ 6 ส.ค. เย็น debit ใช้งานได้ปกติแล้ว แต่ข้อมูล telemetry แสดง code=00 appr=true checkout=true คือ เครื่องกลับมาปกติเอง ไม่ใช่เพราะโค้ดที่แก้

สลิปที่พังเขียน REF. NO.: TBA / CARD TYPE: TBA = host ตอบไม่ครบ (offline / stand-in approval) ซึ่งเข้ากับ Y1/Y3 ที่แก้ไปแล้ว แต่ยังไม่เคยเห็นของจริง
