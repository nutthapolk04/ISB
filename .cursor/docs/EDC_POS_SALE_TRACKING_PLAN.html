แผน EDC POS: Payment Intent + บันทึกรายการซื้อขาย

ISB Campus Card · Store / BookStore POS · อัปเดต 6 ส.ค. 2026
อ้างอิงเคส: EDC อนุมัติ 12,520 บาท (APPR 139350) แต่หน้าเว็บไม่สำเร็จ · สต็อกไม่ถูกหัก

ปัญหาหลักวันนี้
EDC ตัดเงินที่เครื่องแล้ว แต่ POST /pos/checkout ไม่สำเร็จ → ไม่มี receipt, ไม่หักสต็อก, ไม่มี audit trail ใน DB ว่า cart มีอะไร · แคชเชียร์ไม่รู้ว่าควรส่งของให้ลูกค้าหรือไม่

1. สถานะระบบปัจจุบัน

สิ่งที่มีเก็บอะไรข้อจำกัดกับ EDC
receipts + receipt_items ใบเสร็จสมบูรณ์, สินค้า, ราคา, ผู้จ่าย, หักสต็อก สร้างได้เฉพาะเมื่อ checkout สำเร็จเท่านั้น
payment_intents (intent_type=pos_sale) cart_snapshot JSON, สถานะ pending/confirmed ใช้เฉพาะ QR PromptPay (BAY) — EDC ไม่ใช้
audit_logs CREATE receipt หลัง checkout ไม่มี log ก่อน checkout / ไม่มี EDC approval code
EDC Bridge (local) /txn/sale, POS REF, approval อยู่เครื่องแคชเชียร์ ไม่ sync ขึ้น server
Backend access log PC-03 PosController.checkout() [200/4xx] ไม่ log body, ไม่มี approval code / รายการสินค้า
สรุป: รายการสินค้า + ผู้ซื้อ + ราคา มีเก็บแล้ว ใน cart_snapshot ของ POS QR แต่ EDC ยังไม่มี — ต้องเพิ่ม flow เดียวกัน + หน้า admin สำหรับเคสค้าง

2. เป้าหมาย (Goals)

  1. บันทึกรายการซื้อขายก่อนยิง EDC — สินค้า, จำนวน, ราคา, ส่วนลด, ผู้จ่าย (ถ้ามี), ร้าน, แคชเชียร์
  2. ติดตามสถานะทุกขั้น — ตั้งแต่สร้าง intent → รอ EDC → อนุมัติ → checkout → สำเร็จ/ล้มเหลว
  3. แก้เฉพาะหน้าได้ — เคส EDC ผ่านแต่ระบบไม่บันทึก: แคชเชียร์/ผู้ดูแลเห็นรายการ → ส่งของให้ลูกค้า → admin confirm ทีหลัง
  4. ตรวจสอบย้อนหลัง — reconcile สต็อก vs ยอดขาย EDC ที่ค้าง / void ที่ EDC แล้ว
  5. กัน double charge — idempotency จาก bridge key + status guard

3. แนวคิดหลัก: pos_sale_attempt

ขยายจาก payment_intents (reuse pattern ของ POS QR) หรือสร้างตารางใหม่ pos_sale_attempts ที่ผูก 1:1 กับ intent — แผนนี้แนะนำ ขยาย payment_intents เพื่อลด migration ซ้ำซ้อน

4. Lifecycle สถานะ

4.1 สถานะหลัก (payment_intents.status)

Statusความหมายแอคชันที่ทำได้
pending สร้าง intent + cart snapshot แล้ว ยังไม่ยิง EDC ยิง EDC / ยกเลิก
edc_processing กำลังรอลูกค้าแตะบัตร / รอ terminal รอ / timeout → cancelled
edc_approved Terminal อนุมัติ กำลังเรียก checkout รอ checkout
confirmed checkout สำเร็จ มี receipt + หักสต็อก ดู receipt / void ตามปกติ
approved_unrecorded EDC ผ่าน แต่ checkout ล้มเหลว — เคส 12,520 ส่งของได้ (ตามนโยบาย) · admin retry confirm · mark resolved
declined Terminal ปฏิเสธ ลองใหม่ (intent ใหม่)
cancelled แคชเชียร์ยกเลิกก่อน EDC / timeout —
resolved_manual ปิดเคสแล้ว (void EDC / บันทึก manual / ไม่เรียกเก็บ) audit only

4.2 Event types

  • intent_created
  • bridge_sale_started
  • bridge_approved / bridge_declined
  • checkout_started
  • checkout_succeeded / checkout_failed
  • admin_retry_confirm
  • admin_mark_resolved
  • cashier_acknowledged — แคชเชียร์กด "ส่งของแล้ว" (optional)

5. Flow ใหม่ (Store POS + EDC)

[Cashier] เลือกสินค้า → ชำระ EDC │ ▼ POST /api/v1/pos/edc-intent • validate cart • enrich product names • INSERT payment_intents (pos_edc, pending, cart_snapshot) • event: intent_created │ ▼ [Browser] EDC Bridge: POST /txn/sale (idempotency_key จาก server) • PATCH .../edc-intent/:ref/status → edc_processing • event: bridge_sale_started │ ├── Terminal DECLINED → declined + event │ └── Terminal APPROVED (response 00) • PATCH .../edc-result (approval_code, terminal_ref, masked_card) • status → edc_approved • event: bridge_approved │ ▼ POST .../edc-intent/:ref/confirm (เรียก checkout ภายใน) ├── 200 → confirmed + receipt_id + หักสต็อก │ event: checkout_succeeded │ └── fail → approved_unrecorded + failure_reason event: checkout_failed [UI] แสดง ref_code + รายการสินค้า + "ติดต่อผู้ดูแล" [นโยบาย] ส่งของให้ลูกค้าได้ (มีหลักฐานใน DB)

7. Frontend (Store POS)

7.1 EdcPaymentModal.tsx

  • เปิด modal → สร้าง intent ก่อน edc.sale()
  • แสดง Ref บนหน้าจอ (ให้แคชเชียร์แจ้ง IT)
  • หลัง approve → confirm ผ่าน API (ไม่เรียก checkout ตรง)
  • ถ้า approved_unrecorded → modal แสดงรายการสินค้า + คำเตือน ห้ามยิง EDC ซ้ำ

7.2 หน้าจอแคชเชียร์เมื่อค้าง (เฉพาะหน้า)

  • รายการสินค้า + ยอดรวม + APPR code (ถ้ามี)
  • ปุ่ม "พิมพ์สลิปชั่วคราว" (ไม่หักสต็อก — แค่ให้ลูกค้า/ร้านถือ)
  • ปุ่ม optional: "ส่งของให้ลูกค้าแล้ว" → event cashier_acknowledged

  • Export CSV สำหรับ audit

9. นโยบายปฏิบัติการ (Ops)

เมื่อ status = approved_unrecorded
  1. ห้ามกดชำระ EDC ซ้ำ (เสี่ยง double charge)
  2. ตรวจรายการใน Admin จาก ref / APPR code
  3. ส่งของให้ลูกค้าได้ตามรายการใน snapshot (นโยบายร้าน)
  4. Admin กด Retry confirm — ถ้าสำเร็จ → สต็อกหัก + มี receipt
  5. ถ้า void ที่ EDC แล้ว → Mark resolved + note

10. แผนดำเนินงาน (Phases)

Sprint 1 — MVP ป้องกันข้อมูลหาย (ประมาณ 3–5 วัน)

  • Migration: ขยาย payment_intents + สร้าง pos_sale_attempt_events
  • pos_edc_service.ts: create / edc-result / confirm / get
  • Enrich cart_snapshot ด้วยชื่อสินค้า + payer label
  • Frontend: EdcPaymentModal ผูก intent flow
  • UI error state: แสดงรายการสินค้าเมื่อ approved_unrecorded
  • Tests: approve → confirm OK; approve → confirm fail

Sprint 2 — Admin & Reconcile (ประมาณ 3–4 วัน)

  • หน้า Admin: รายการ attempts + filter + detail drawer
  • Retry confirm + Mark resolved
  • Export CSV
  • Structured log บน PC-03 เมื่อ confirm จาก EDC intent

Sprint 3 — แข็งแรงขึ้น (optional)

  • สลิปชั่วคราว (ไม่หักสต็อก) จาก cart_snapshot
  • ปุ่ม cashier_acknowledged
  • Alert email/Slack เมื่อ approved_unrecorded
  • EDC bridge webhook → server (ถ้าแก้ Paywire bridge ได้)
  • ขยาย pattern เดียวกันไป Canteen POS (ถ้าใช้ EDC)

11. SQL ตรวจสอบ (หลัง deploy)

-- เคสค้างที่ EDC ผ่านแต่ยังไม่มี receipt
SELECT ref_code, status, amount, edc_approval_code, edc_terminal_ref,
       payer_label, cart_snapshot, created_at, failure_reason
FROM payment_intents
WHERE intent_type = 'pos_edc'
  AND status IN ('approved_unrecorded', 'edc_approved')
ORDER BY created_at DESC;

-- รายการสินค้าใน snapshot (PostgreSQL JSON)
SELECT ref_code,
       jsonb_array_elements(cart_snapshot->'items') AS line_item
FROM payment_intents
WHERE ref_code = 'EDC-20260806-XXXX';

12. Out of scope (รอบนี้)

  • Auto void EDC จากระบบ
  • Kiosk EDC top-up (flow แยก)
  • แก้ไขเคส 12,520 ย้อนหลัง (ไม่มีข้อมูลใน DB — ต้อง manual จากใบ EDC)

13. เกณฑ์สำเร็จ (Acceptance)

  • ทุกครั้งที่เปิด EDC payment มี row ใน payment_intents พร้อม cart_snapshot ก่อนยิงเครื่อง
  • เคส EDC approve + checkout fail → status approved_unrecorded + เห็นรายการสินค้าบน admin
  • Admin retry confirm สำเร็จ → มี receipt + สต็อกถูกหักครั้งเดียว
  • ค้นหาด้วย APPR code / ref_code / วันที่ได้
  • ไม่มี double receipt เมื่อ retry confirm ซ้ำ
