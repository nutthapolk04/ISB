โค้ดที่ทำให้เงียบ

frontend/src/pages/store/EdcPaymentModal.tsx — เดิมเรียก checkout เฉพาะเมื่อมี approval code:

if (nextApprovalCode.trim().length > 0) {
    ... await onConfirm(...)      // ← เรียก /pos/checkout ตรงนี้ที่เดียว
} else {
    setApprovedNoRecord(true);    // ← ไม่ติดต่อ server เลย จบแค่หน้าจอ
    setStep("declined");
}

เครื่องตอบ responseCode = "00" (อนุมัติ · ปรินท์สลิปแล้ว) แต่ approvalCode ว่าง → เข้า branch ล่าง → ขึ้นจอเหลือง "APPROVED — NOT RECORDED" → **ไม่มี network request ออกไปเลย** → ไม่มี receipt · ไม่หักสต็อก · ไม่มี log

ทำไม approval code ถึงว่าง — ยังเป็นสมมติฐาน
frontend/src/lib/paywire/client.ts map แบบนี้: 
const approvalCode    = raw.approvalCode ?? fields["approval_code"];
const maskedPan       = fields["30"];               // VTI numeric
const rrn             = fields["D3"] ?? fields["ref_no"];
const responseMessage = fields["response_msg"] ?? fields["02"];
masked PAN / RRN / message มี fallback เป็นเลข VTI แต่ approvalCode ไม่มี ถ้าเครื่องส่ง auth code มาเป็น fields["38"] (ISO-8583 field 38) เราจะมองไม่เห็น

เคสนี้เป็น debit card ซึ่งอาจ map ไม่เหมือน credit ยืนยันไม่ได้จนกว่าจะเห็น payload จริง — ซึ่งเป็นเหตุผลที่ระยะ 1 มาก่อนระยะ 2

3 กติกาที่ห้ามพลาด

  1. log ก่อนแตก branch — เส้นทางเงียบคือเส้นที่ต้องบันทึกที่สุด
  2. fire-and-forget — ไม่ await ไม่ throw การขายต้องไม่พังเพราะ log (controller ตอบ 200 แม้ insert ล้ม)
  3. ยิงไม่ออกให้คิวไว้ — เน็ตร้านเป็นผู้ต้องสงสัย เก็บ localStorage สูงสุด 50 รายการ แล้ว flush ตอนยิงสำเร็จครั้งถัดไป

คอลัมน์ที่ตอบคำถามได้ทันที

คอลัมน์ทำไมต้องมี
checkout_attempted ตัวชี้ขาด — false = POS ยอมแพ้โดยไม่ถาม server เลย
has_approval_code เก็บแยกไม่ derive จาก approval_code IS NULL เพราะต้อง match กฎ trim() ของ frontend เป๊ะๆ
fields (jsonb) field bag ดิบ — คำตอบว่า approval code อยู่ key ไหน อยู่ในนี้
event started ครอบเคสที่เครื่องตัดเงินแล้วไม่ตอบอะไรเลย · error = bridge พัง
client_at vs created_at ต่างกันเมื่อ row ถูกคิวไว้ตอน offline แล้วส่งทีหลัง
PCI — fields เก็บดิบเพราะจำเป็น แต่ไม่มีทางเก็บ PAN ได้:
  • redact ค่าที่เป็นเลข 13–19 หลัก (มี/ไม่มีเว้นวรรค-ขีด) → masked card ****8433 รอด
  • blank key ที่มีคำว่า track / pin / pan / cvv / emv / icc / ksn / dukpt (เก็บชื่อ key ไว้ เพราะต้องรู้ว่าเครื่องส่งอะไรมา)
  • cap 80 field · value 512 ตัวอักษร
  • scrub 2 ชั้น — browser (ขอบเขตจริง PAN ไม่ออกจากเครื่อง) + backend (กัน client เก่า/ปลอม)

ระยะ 2 — แก้ต้นเหตุ

รอข้อมูลจากระยะ 1
  • รอ EDC ยิงจริงบน prod สัก 1–2 วัน แล้วดูว่า fields มี key อะไร
  • เพิ่ม fallback ให้ approvalCode ตาม key ที่เจอ (คาดว่า "38")
  • เขียน test ล็อกการ map ไว้
ห้ามเดาแก้ก่อน — หยิบ field ผิดมาเป็น approval code จะได้ใบเสร็จที่มีเลขอนุมัติผิด ซึ่งแย่กว่าไม่มีใบเสร็จ เพราะ reconcile กับธนาคารไม่ได้และไม่มีใครรู้ตัว

SQL ที่จะใช้ตอบคำถามนี้:

-- เคสที่เครื่องอนุมัติแต่ POS ไม่ยิง checkout (ใช้ partial index)
SELECT created_at, shop_id, amount, approval_code, fields
FROM edc_txn_events
WHERE response_code = '00' AND checkout_attempted = false
ORDER BY created_at DESC;

-- key ที่ bridge ส่งมาจริง เรียงตามความถี่
SELECT k, count(*)
FROM edc_txn_events, jsonb_object_keys(fields) AS k
WHERE event = 'result'
GROUP BY k ORDER BY count(*) DESC;

หรือ grep จาก backend log ได้เลย: grep '\[EDC\] terminal event' | grep fieldKeys

ระยะ 3 — ไม่ให้เป็นทางตัน

ยังไม่ทำ

ตอนนี้เจอจอเหลืองแล้วกดอะไรไม่ได้เลยนอกจาก Back

เพิ่มผล
ส่ง posRef เข้า sale() ปลดล็อก query() ที่ SDK มีอยู่แล้ว — comment ในโค้ดเขียนว่า "recover a sale whose response was lost (timeout)" ตอนนี้ส่งแค่ idempotencyKey เลยเรียก query ไม่ได้
ปุ่ม "ตรวจสอบรายการล่าสุด" เรียก query(posRef) ดึง approval code กลับมาเอง
ช่องกรอก APPR จากสลิป ทางออกสุดท้าย + audit ว่าใครกรอก (pos_checkout_service.ts บังคับ edc_approval_code ไม่ว่าง → ถ้าไม่มีช่องนี้ retry จะได้ 400 ตลอด)
timeout + AbortController ใน api.ts ตอนนี้ไม่มี fetch แขวนได้ไม่จำกัด + dismissLocked ทำให้ปิด modal ไม่ได้ → จอค้าง "Recording receipt…" ตลอดกาล

เก็บ field ที่ void() ต้องใช้ให้ครบตั้งแต่ตอนนี้ (invoice · posRef · transactionId · cardApprovalCode) แม้ยังไม่ทำ auto-void — ไม่ต้อง migrate รอบสอง

ระยะ 4 — intent + admin UI

ยังไม่ทำ

คือแผนฉบับแรกทั้งหมด: สร้าง intent + cart snapshot ก่อนยิงเครื่อง แล้วมีหน้า admin ให้ retry / reconcile

ยังควรทำ ประโยชน์คือ "รู้ว่าตะกร้ามีอะไร" แต่ไม่ได้แก้ต้นเหตุนี้ → อยู่ท้ายสุด

5 จุดที่ต้องแก้จากแผนฉบับแรกก่อนลงมือ

แผนเดิมเขียนว่าต้องเปลี่ยนเพราะ
เพิ่ม status 5 ตัวใน payment_intents.status status เป็น Postgres ENUM paymentintentstatus มีแค่ pending / confirmed / cancelled — ALTER TYPE ADD VALUE ใช้ค่าใหม่ใน transaction เดียวกันไม่ได้ และ Drizzle รัน migration ใน transaction → migration พัง
ทางแก้: คอลัมน์ edc_status varchar แยก อย่าแตะ enum เดิม
bridge_idempotency_key = POS REF ใน SDK เป็น คนละ field — QueryRequest.posRef vs idempotencyKey → ต้องเก็บ 2 คอลัมน์ ไม่งั้น query() เรียกไม่ได้
Admin กด "Retry confirm" ได้ 400 ทันทีถ้าไม่มี approval code (backend บังคับ) → ต้องมีช่องกรอกก่อน (ระยะ 3)
"ไม่มี double receipt เมื่อ retry ซ้ำ" ไม่มี unique index กันที่ DB เลย (มีแค่บน receipt_number) → ลอก 3-phase claim จาก pos_qr_service.ts (ใช้ค่า sentinel ต่างกัน ไม่งั้นชน logic QR) + partial unique index เป็นตาข่ายชั้นสอง
กังวลว่า retry จะติด "สต็อกหมด" checkout ไม่ block สต็อกไม่พอ — มันหักลงติดลบ
ข่าวดี: retry ไม่พัง · ข่าวร้าย: ระหว่างค้าง ระบบขายของชิ้นเดิมซ้ำได้

3. ผลกระทบของระยะ 1

ไม่กระทบอะไรเลย — เป็นการเพิ่มล้วน
  • DB: ตารางใหม่ 1 ตัว ไม่มี ALTER บนตารางเดิม ไม่แตะ payment_intents → rollback = DROP TABLE
  • เส้นทางการขาย: ไม่แตะ /pos/checkout · pos_checkout_service · wallet · stock · receipt เลย
  • modal: prop telemetry เป็น optional → ถ้าลืมส่ง ก็ log เป็น "unknown" ไม่ crash
  • ถ้า telemetry ล้มทั้งหมด: การขายเดินต่อได้ปกติเหมือนก่อนมีระบบนี้
  • สิทธิ์: เขียนได้ = cashier / manager / admin / kiosk · อ่านได้ = manager / admin เท่านั้น (traffic ดิบของเครื่อง ไม่ใช่ feature ของ POS)

ที่ยังต้องเฝ้า

เรื่องสถานะ
ตารางโตเรื่อยๆ ~3 row ต่อการขาย EDC 1 ครั้ง (started + result + อาจมี error) append-only ไม่มีใครอ่านใน hot path → prune ด้วย created_at ได้ ยังไม่มี retention policy — ควรตั้ง
คิว localStorage cap 50 รายการ เกินแล้วทิ้งตัวเก่าสุด ไม่ล้าง quota ไม่เคลียร์ตอน logout (เหมือน inventory_batch_queue_v2)
context: "unknown" ถ้ามี call site ใหม่ที่ลืมส่ง prop จะเป็น unknown — ไม่ error แต่ต้องคอยดู

5. ขั้นตอน deploy ระยะ 1

  1. deploy backend แล้วรัน bun run db:migrate (สร้างตารางใหม่ 1 ตัว ไม่ต้อง downtime)
  2. deploy frontend (dist ผ่าน SFTP ตามเดิม)
  3. ยิง EDC ทดสอบ 1 ครั้งบน prod แล้วเช็ค: 
    grep '\[EDC\] terminal event' /path/to/backend.log | tail -5
  4. ปล่อยเก็บข้อมูล 1–2 วัน แล้วดู key ที่ bridge ส่งมาจริง → เริ่มระยะ 2

ลำดับ backend-ก่อน-frontend สำคัญ: frontend ที่ยิง /pos/edc-events ไปยัง backend เก่าจะได้ 404 แต่เพราะ fire-and-forget มันจะเข้าคิวแล้วส่งใหม่ทีหลัง ไม่กระทบการขาย

6. ยังต้องตัดสินใจ

  1. ถามแคชเชียร์ก่อนเลย (ฟรี) — เห็นจอเหลือง "APPROVED — NOT RECORDED" หรือจอแดง / toast แดง "Checkout failed"? แยกได้ทันทีว่าเป็นเส้นทางไหน โดยไม่ต้องรอข้อมูลใหม่
  2. retention ของ edc_txn_events — 90 วัน? 1 ปี? (มี PII น้อย ไม่มี cart แต่มี masked card)
  3. นโยบายส่งของตอนค้าง — แคชเชียร์ตัดสินเองได้ หรือต้องมีคนอนุมัติ
  4. ระยะ 4 ครอบ Canteen + Cashier EDC top-up ไหม — ใช้ modal ตัวเดียวกันทั้ง 3 ที่ (top-up ไม่มี cart เลย) ตอนนี้ระยะ 1 ครอบทั้ง 3 แล้ว

7. Out of scope

  • Auto void EDC จากระบบ
  • Kiosk EDC top-up (flow แยก)
  • แก้เคส 12,520 ย้อนหลัง — ไม่มีข้อมูลใน DB ต้อง manual จากใบ EDC (ทำหลังระยะ 4 ผ่าน flow ใหม่จะได้ audit trail ครบ ดีกว่า INSERT receipt ตรงๆ)
  • หน้า UI สำหรับดู edc_txn_events — ระยะ 1 ใช้ SQL / grep log ก่อน (API GET /pos/edc-events พร้อมแล้วถ้าจะทำ)
