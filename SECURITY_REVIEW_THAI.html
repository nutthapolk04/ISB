ปัญหา #1: EDC Approval Code ไม่ Validate
🔴 CRITICAL
🎯 ปัญหาคืออะไร:
เมื่อผู้ใช้ขอ top-up โดยใช้ EDC (บัตรเครดิต) ระบบ ยอมรับ approval code โดยไม่ถามเก็บเงินจริง จาก payment gateway
📍 สถานการณ์ Attack:
แฮกเกอร์ส่งคำขอ:
{ "amount": 10000, "edc_approval_code": "FAKE-12345", ← ปลอม "edc_terminal_ref": "arbitrary", "edc_masked_card": "****1234" } ผลลัพธ์: ✅ เพิ่มเงิน 10,000 บาท ❌ ไม่มีการเก็บเงินจริงผ่าน Paywire
💥 ทำให้เสียหาย:
• 💰 สูญเสียเงินสดแบบกลับไม่ได้
• 📊 ยอดเก็บเงินในรายงานไม่ตรง
• 🔓 ใครก็ได้ top-up เงินได้ฟรี
📍 ไฟล์ที่เกี่ยวข้อง:
• backend-bun/src/services/topup_service.ts บรรทัด 947-952
• backend-bun/src/controllers/TopupController.ts บรรทัด 52-66
✅ วิธีแก้:

1. Verify EDC Code กับ Gateway:
const verified = await verifyEdcApprovalCode({ approvalCode: args.approvalCode, terminalRef: args.terminalRef, expectedAmount: args.amount, }); if (!verified) { throw new Error("EDC code invalid or verification failed"); }
2. หลังจาก verify ✅ ถึงเพิ่มเงิน
3. Implement idempotency ป้องกัน duplicate submission
4. ใช้ reference ticket pattern (เหมือนระบบ payment intent)
⏰ ลำดับความสำคัญ: FIX NOW!
ปัญหา #2: EDC Field ไม่มี Format Validation
🔴 HIGH
🎯 ปัญหาคืออะไร:
ระบบยอมรับ Approval Code ยาวเท่าไหร่ก็ได้ (ไม่มีขีดจำกัด) และไม่เช็ค format
📍 สถานการณ์ Attack:
แฮกเกอร์ส่ง:
edc_approval_code = "AAAA...AAAA" (100,000 ตัวอักษร) ผลลัพธ์: ❌ ระบบเก็บลงฐานข้อมูล → ตัดหรือเก็บผิด ❌ Log file มีขยะ → ทำให้ระบบช้า ❌ Hardware crash → ถ้า device ที่เชื่อมต่อรับค่า
✅ วิธีแก้: เพิ่ม Format Validation
edc_approval_code: String({ minLength: 1, maxLength: 50, pattern: '^[A-Z0-9]+$' ← ตัวใหญ่กับตัวเลขเท่านั้น }) edc_terminal_ref: String({ maxLength: 20, pattern: '^[A-Z0-9\\-]+$' }) edc_masked_card: String({ maxLength: 20, pattern: '^\\*{4}\\d{4}$' ← รูปแบบ ****1234 })
🟠 ปัญหาสำคัญ (High/Medium-High Priority)
ปัญหา #3: Path Traversal ในชื่อ Report
🟠 HIGH
🎯 ปัญหาคืออะไร:
เมื่อ export report เป็น PDF ชื่อไฟล์มาจากวันที่ที่ผู้ใช้กรอก (ไม่มีการตรวจสอบ)
📍 สถานการณ์ Attack:
เดือน: "../../" ← ตัดสินใจเองได้ → ชื่อไฟล์: "Report_../../_any.pdf" → Browser อาจบันทึกไปตำแหน่ง ../ ได้
✅ วิธีแก้: ลบ `../` และ `/` ออกจากชื่อไฟล์ทั้งหมด
ปัญหา #4: Barcode ไม่มี Max Length
🟠 MEDIUM-HIGH
🎯 ปัญหาคืออะไร:
ผู้ใช้ส่ง barcode ยาว 10,000 ตัวอักษร (ไม่มีขีดจำกัด)
📍 ผลลัพธ์:
❌ Print label พัง → ตัดหลายบรรทัด ❌ Barcode scanner ไม่อ่านได้ ❌ ฐานข้อมูล overflow
✅ วิธีแก้: Barcode ไม่เกิน 100 ตัวอักษร (จริงๆ 8-15 ตัว)
🟡 ปัญหากลาง (Medium Priority)
ปัญหา #5 & #6: localStorage + XSRF
🟡 MEDIUM
📍 ปัญหา #5: localStorage Counter Poisoning
ใช้ localStorage เก็บเลขที่ report (ISB001, ISB002, ...) แต่ไม่มีการตรวจสอบค่า

Attack: Tab ที่เป็นอันตรายเขียน localStorage → Report ID ยุ่งเหยิง
📍 ปัญหา #6: Missing XSRF Token
Top-up & Payment endpoints ไม่มี XSRF token validation
📍 สถานการณ์ Attack:
Attacker: ทำเว็บไซต์เด็ดขาด (evil.com) ผู้ใช้: คลิกเข้า evil.com ขณะ logged-in เข้า ISB evil.com ทำการ: → ส่งคำขอ top-up ด้วยชื่อผู้ใช้ → Browser ส่ง cookie โดยอัตโนมัติ → ผู้ใช้เสียเงินโดยไม่รู้ตัว
ปัญหา #7 & #8: N+1 Query (Performance)
🟡 MEDIUM
🎯 ปัญหาคืออะไร:
เมื่อแสดง 100 wallet ระบบทำ query 100 ครั้ง (ทีละอัน) แทนที่จะทำ 1 ครั้ง
📍 ตัวอย่าง Bad Code:
❌ for (const wallet of wallets) { const user = await db.query('SELECT * FROM users WHERE id = ?', wallet.user_id); } // 100 wallets = 100 queries ✅ const userIds = wallets.map(w => w.user_id); const users = await db.query('SELECT * FROM users WHERE id IN (?)', [userIds]); // 100 wallets = 1 query
💥 ผลลัพธ์:
• 👨‍👩‍👧‍👦 Family Dashboard ช้า 100 เท่า
• 📜 Receipt History บ้าน/เลื่อนไม่ไหว

✅ สิ่งที่ดี (ไม่ต้องแก้)

  • SQL Injection: ปลอดภัย (ใช้ Drizzle ORM safe parameterization)
  • Authorization: เช็ค permission ถูกต้องก่อนทำ operation
  • Transaction Lock: ใช้ SELECT FOR UPDATE ป้องกัน race condition
  • Data Isolation: ไม่มีข้อมูล customer จาก shop อื่น (shop scoping ดี)
  • Balance Protection: มีขีดจำกัดยอดเงินใน wallet (฿50,000)
